# torsor-helper v0.4 "Token Thrift" — Design

**Goal:** Cut LLM token/cost spend by (1) letting torsor **learn the deterministic things agents do repeatedly** so they're fetched once instead of re-derived every session, and (2) letting you **route a cheap model to that basic, deterministic work** while the smart model only thinks and constructs. Hold every invariant: local-first, Markdown is the source of truth, the SQLite index is rebuildable, deterministic + offline, no required cloud/paid deps.

**Why this saves tokens (the mechanism):** the expensive tokens in agentic coding are *re-derivation* — re-discovering how to run the tests, re-grepping for callers, re-reading files to answer a question that has an exact deterministic answer. torsor already turns much of that into one cheap tool-call. v0.4 adds the missing pieces: a **learned command book** (stop re-deriving project commands), a **frequency log → recipes** (see which deterministic lookups recur), and a **model-routing policy** (do the recurring deterministic work on a cheap model; reserve the frontier model for genuine reasoning). torsor itself never calls an LLM — it *publishes* the policy into the agent's prompt file and as a tool, for the harness/agent to follow.

---

## Feature A — Command book (learn & replay project commands)
The agent rediscovers "how do I run tests/lint/build here?" every session. Record it once.
- `paths.commands_file = .torsor/commands.md` — Markdown source of truth, human- and agent-editable. Body lines: `- **<name>**: \`<command>\` — <note>`.
- `operations.record_command(store, name, command, note="")` (upsert), `list_commands(store)` (parse → `[{name, command, note}]`), `run_command(store, name)` (subprocess; CLI only).
- CLI `torsor commands` (list) · `torsor commands --add 'name=cmd' [--note ...]` · `torsor commands --run <name>`.
- MCP `record_command(name, command, note)` + `list_commands()` (returns the book; the agent runs commands with its own shell — torsor doesn't execute arbitrary commands from the server).
- Surfaced in `project_primer` so every session sees the commands at prompt time (zero discovery calls).

## Feature B — Op log → recipes (learn what recurs)
torsor records which deterministic read-tools the agent calls, and how often — the "commands the LLM does repeatedly."
- `db.op_log(op TEXT, args TEXT, hits INTEGER, last_used INTEGER, PRIMARY KEY(op,args))` (SCHEMA_VERSION → 6, additive) + a monotonic `op_clock` meta counter. `db.log_op(conn, op, args)` (upsert hits+1), `db.top_ops(conn, limit)`.
- `operations._log_op(store, op, args)` — best-effort (never breaks a tool), called at the entry of the deterministic read-ops: `recall`, `get_intent`, `find_targets`, `impact`, `check_drift`, `check_dependencies`, `agent_rules`.
- `operations.recipes(store, limit=10)` → top `(op, args, hits)`. CLI `torsor recipes`; MCP `recipes()`.
- These are exactly the calls to route to the cheap model (Feature C), and a signal of what to bake into the primer/command book.

## Feature C — Model tiering (cheap for basic, smart for thinking)
- `config.ModelsConfig(cheap: str = "", smart: str = "", fast: str = "")` added to `TorsorConfig.models`. Persisted in `torsor.toml [models]`.
- `operations.model_policy(store, config)` → a Markdown **routing policy** digest from `config.models` + a built-in default op→tier map: deterministic torsor lookups + command replays → **cheap**; designing/writing/refactoring/deciding → **smart**.
- `operations.write_model_policy(store, config, target)` injects a marker-delimited `## Model routing` block into AGENTS.md/CLAUDE.md (reuses `_write_managed_block`). MCP `get_model_policy()` returns the same.
- CLI `torsor models` (show current + policy) · `torsor models --cheap <id> --smart <id> [--fast <id>]` (set + save) · `torsor models --write [AGENTS.md]` (inject the block).
- torsor does NOT call models — it declares the policy for the orchestrating harness/agent (e.g. Claude Code subagents, multi-model routers) to follow.

## Out of scope (so we don't over-reach or mislead)
- torsor calling/billing LLMs itself, or *enforcing* model routing — it can only declare the policy; the harness routes.
- Caching deterministic *answers* with a stored result + invalidation — risk of serving a stale "exact" answer. Instead we (a) keep the deterministic tools exact-by-construction, and (b) track *frequency* to inform routing. Frequency, not stale cache.

## Build order
C (model tiering — self-contained, explicitly requested) → A (command book) → B (op log + recipes) → README "Token thrift" section (detailed usage) → review → merge. Each: TDD, full suite green between tasks.

## Tests (offline, deterministic)
- C: `ModelsConfig` round-trips through `save/load_config`; `model_policy` renders cheap/smart ids; `--write` injects an idempotent block; `get_model_policy` non-empty.
- A: `record_command`/`list_commands` round-trip + upsert; `commands.md` is valid Markdown; primer includes a recorded command; `--run` executes (smoke).
- B: `log_op`/`top_ops` round-trip + hit counting; a repeated `get_intent` call raises its hit count; `recipes` ranks by hits; SCHEMA_VERSION == 6.
